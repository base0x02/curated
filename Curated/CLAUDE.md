# Curated (Mac)

A personal SwiftUI Mac app for intentional watching. The user picks TikTok creators and YouTube creators (Shorts, long videos or both). Curated downloads their recent videos with yt-dlp, usually overnight, and plays them with no feed or recommendations: per-creator queues, Automix, Top 15, category Automix/Top 5, Time Limit, Watch Later and Bookmarks. It is also the sync server for the Android (`../CuratedAndroid`) and iOS (`../CuratediOS`) companions. Those apps only play videos; every download happens on the Mac.

The user runs this app every day. **Never test against the real data folder, the real library or port 8765** (see "Testing" below).

## Build and run

- SwiftPM only, no Xcode project. macOS 14+, Swift 6 tools in Swift 5 language mode.
- `./build.sh` builds `./Curated.app`; `./build.sh --install` also replaces `~/Applications/Curated.app`. Check `pgrep -x Curated` first, and if it's running, ask the user to quit it.
- The Liquid Glass icon (`Resources/CuratedAppIcon.icon`) needs Xcode's `actool`. If the active developer dir is the Command Line Tools, build with `DEVELOPER_DIR` pointing at a full Xcode.
- Runtime dependencies: `yt-dlp` and `ffmpeg` from Homebrew (found via `Tools.find`, which also covers launchd's minimal PATH).
- The version lives in `VERSION` / `BUILD_NUMBER` at the top of `build.sh`. It moves in step with the Android and iOS apps, and releases are tagged `vX.Y`. `../dev-readme.md` has the full release and install routine.

## How data is stored

There is no database. Everything is either JSON files in the data folder, or video files plus small sidecar files in the library folder. The library listing is rebuilt by **scanning the folders** (`AppModel.reloadLibrary()` → `Library.scan`) at launch, whenever the app becomes active (to pick up overnight downloads), and after downloads, deletes and creator changes.

### Data folder: `~/Library/Application Support/Curated/`

`Paths.appSupport`; the `CURATED_DATA_DIR` environment variable overrides it.

| File | Contents | Written by |
|---|---|---|
| `config.json` | `Config`: `settings` (`AppSettings`), `creators` (`[Creator]`), `categories` (`[Category]`). Pretty-printed, sorted keys | `AppModel.config` didSet → `Config.save()` |
| `state.json` | `RunState`: `lastRun`, `lastShortRun` and `lastLongRun` (the last finished run that included short or long videos; optional) plus per-creator `CreatorRunInfo` (date, newVideos, removed, error, lastSuccess, belowMinViews), keyed by creator id. ISO 8601 dates | `RunState.update` (NSLock'd read-modify-write); also written by the headless job |
| `played.json` | `{videoID: {"played": Bool, "at": ISO8601}}` | `PlayedStore` |
| `watchlater.json` | `{videoID: {"saved": Bool, "at": ISO8601}}` | `WatchLaterStore` |
| `bookmarks.json` | Same shape as `watchlater.json` | `BookmarkStore` |
| `positionmarks.json` | `{videoID: {"seconds"?: Double, "at": ISO8601}}`: where each long video was left off, so it resumes there on any device. Saved every 5 s of playback, on pause, on switching videos and on quit, but only if playback moved (re-saving an old place would date it as new and beat a phone's newer one). Cleared (no `seconds`, new date) when the video is watched or nearly finished. Merged with phones through `POST /positions`, and a paused player showing that video moves there | `Playback.savePosition` → `AppModel.setResumePosition`, `AppModel.mergePositions` |
| `handpicked.json` | `{videoID: ISO8601}`: long videos picked by hand from Older Videos, and when. They come first until watched | `AppModel.startPickedDownload` |
| `ipod.json` | `{videoID: ISO8601}`: videos exported for an iPod, and when (the sidebar's iPod list). Mac only, never synced | `AppModel.addToIPodList`, `clearIPodList` |
| `positions.json` | The pre-sync `{videoID: seconds}`. Only read, when `positionmarks.json` doesn't exist yet (its positions are dated 1970 so any newer change wins) | Older builds |
| `sync.json` | `[SyncDevice]`: id, name, **SHA-256 hash of the token** (never the token itself), pairedAt, lastSync | `SyncStore` |
| `download.lock` | Empty file used with `flock`, so the app and the scheduled job never download at the same time | `DownloadLock` |
| `logs/scheduled.log` | stdout/stderr of the overnight job | launchd |
| `logs/downloads.log` | Every download run, from the app or the overnight job: timestamped `[INFO]`/`[ERROR]`/`[DETAIL]`/`[DEBUG]` lines, as much as `settings.logLevel` asks for. Rotated to `downloads.1.log` past 5 MB | `DownloadLog` |
| `config.unreadable-<unix ts>.json` | Backup made when `config.json` fails to decode, before a fresh config is used | `Config.load()` |

Outside the data folder: `~/Library/LaunchAgents/local.curated.download.plist` runs the app binary with `--scheduled-download` at each of `settings.scheduleTimes`: `scheduleHour:scheduleMinute` (which older builds also read) plus `extraScheduleTimes`, as an array of `StartCalendarInterval`s. Runs missed while the Mac sleeps coalesce into one on wake, and `DownloadLock` skips a run if another is going. `Scheduler.sync` rewrites it whenever settings change, and skips that entirely when `CURATED_DATA_DIR` is set.

UI-only preferences (sort order, collapsed sections, queue visibility) are in `UserDefaults` via `@AppStorage`: `creatorSort`, `groupCreatorsByCategory`, `otherCreatorsExpanded`, `vineExpanded`, `queueHidden`. `Playback` keeps `longAutoplay` and `shortAutoplay` (short videos go on to the next one when they end, or loop; on by default) there too.

### Library folder: `~/Movies/Curated/` (`settings.libraryPath`, changeable in Settings)

One folder per creator, named by `Creator.id`: the TikTok username (e.g. `somecreator/`), or `youtube@<handle>/` for YouTube. TikTok usernames can't contain `@`, so the two never clash. This main folder holds the creator's short videos plus their avatar, profile and channel id.

A YouTube creator with long videos turned on (`Creator.longForm`) also has `youtube-long@<handle>/` (`Library.folder(for:form:settings:)`), with the same video, `videos.jsonl`, `views.json` and `archive.txt` files but no avatar or profile (those are read from the main folder). Keeping long videos in their own folder is what keeps them out of the age-based cleanup and out of phone sync, which only look at main folders. They're scanned into `AppModel.longLibraries`, separate from `libraries`.

| File | Contents |
|---|---|
| `<unix timestamp>_<video id>.jpg` | Long videos only: YouTube's thumbnail (`--write-thumbnail`), used as the poster in thumbnails. Removed along with the video |
| `<unix timestamp>_<video id>.mp4` (also `.m4v`/`.mov`) | The video. **The filename is the source of truth** for the video's id and post date (`Library.parseFilename`); a file that doesn't match the pattern is ignored |
| `videos.jsonl` | One JSON line per downloaded video, appended by yt-dlp `--print-to-file`: `id, title, description, timestamp, duration, view_count`. Supplies the caption and duration |
| `views.json` | `{videoID: viewCount}`, merged with the fresh listing on every download run; takes priority over `videos.jsonl`'s count |
| `archive.txt` | yt-dlp `--download-archive` (`<extractor> <id>` per line). A listed video is never downloaded again, even after its file is deleted. Videos skipped by `minViews` are left out on purpose, so they're checked again next run |
| `loudness.txt` | Short videos only: one video id per line, each already measured by `Loudness` (and rewritten if it needed it), so it's never done twice. A missing file means every video there is done on the next download |
| `profile.json` | `{"nickname": ...}`, the display name |
| `avatar.jpg` | Creator avatar |
| `channel_id.txt` | YouTube only: the cached `UC…` channel id (used for the `UUSH…` Shorts and `UULF…` long-video RSS feeds) |

### Rules that keep this working

- **Video ids are the global key.** Played, Watch Later, bookmarks and the sync API are all keyed by the bare video id (TikTok or YouTube id), not by creator or path.
- **Marks are timestamped so devices can merge them.** Each mark records its state and when it last changed. Merges (`mergePlayed`, `mergeWatchLater`, `mergeBookmarks`) keep the newest `at` per id, which is how "unwatch" and "remove" sync too. Never delete a mark to clear it; set it to false with a new date.
- **Old files must keep loading.** Decoders use `decodeIfPresent` with defaults (`Creator`, `Category`, `AppSettings`, `Config`), and `PlayedStore` still reads the pre-1.2 plain-array format. New fields must be optional or defaulted, and existing keys must not be renamed or removed, so older builds (e.g. after a rollback to a `vX.Y` tag) and newer builds can read each other's files.
- **Write atomically.** All writes use `.atomic`. Stores save on every change via `didSet`, so avoid mutating them in tight loops (build a copy, then assign once).
- **Short and long (`VideoForm`):** `Creator.shorts` / `Creator.longForm` (YouTube only; TikTok is always short) pick what's downloaded. `AppModel.form` is which sidebar is showing; it always starts as short. Long videos have their own mixes (Latest, Automix; no Top list) and their own Watch Later and Bookmarks lists, but share the played/Watch Later/bookmark files, keyed by video id like everything else. The `days` window decides which new long videos are downloaded, but long videos are never deleted for their age, so one picked from Older Videos stays however old it is. It keeps its real upload date, but `AppModel.handPicked` (`handpicked.json`) puts it first in Latest, Automix and its creator's gallery until it's watched (`handPickedFirst`), and phones get the same through the manifest's `pickedAt`.
- **Keep by count (`Creator.keepVideos`, `keepHistorical`):** short videos only; nil uses the `days` window. Each download fetches just enough to get the folder back to `keepVideos` unwatched files (played ids from `played.json`): posts newer than the newest video ever downloaded (`Library.newestDownloadDate`, which also reads `videos.jsonl`), oldest of them first; then, with `keepHistorical` or when nothing has been downloaded yet, older never-downloaded ones, newest first (TikTok: a deeper yt-dlp listing; YouTube: the RSS feed, then a flat listing of the `UUSH…` playlist). Watched and archived ids are never fetched. These creators skip the age-based cleanup. Long videos still use `days`.
- **Playlists:** a pasted YouTube playlist link becomes a `Creator` with `playlist = true` (`username` is the playlist ID, key and folder `youtube-playlist@<ID>`). Long videos only, the whole playlist or just its newest N (`playlistLimit`, chosen by the approximate upload dates yt-dlp's `youtubetab:approximate_date` gives each entry, whatever the playlist's order), no day window, never age-deleted, at the creator's resolution. The folder holds the videos plus `profile.json` (the playlist's title), `order.json` (its video IDs in playlist order, which the gallery follows) and the usual `videos.jsonl`, `views.json` and `archive.txt`. Playlists have no category: they're the Playlists group in Creators & Downloads and the last card in the long sidebar, and `mixLibraries` keeps them out of Latest, Automix and Top.
- **Suggestions playlist:** `Creator.suggestions` (`isSuggestions`; key and folder `youtube-playlist@suggestions`) is a made-up playlist like Vine's authors: never in `config.creators`, so Total, the overnight job and older builds never see it. `reloadLibrary` adds it to `longLibraries` once its folder exists, so it's a playlist card in the long sidebar and syncs to phones as a playlist. The engine skips its listing (it only downloads `only` ids); `addToSuggestions` writes its `profile.json` and puts new picks at the front of `order.json`. Already-downloaded, watched or archived ids are never suggested again.
- **YouTube upload times:** yt-dlp sometimes can't date a YouTube video and names it `NA_<id>.mp4`. `DownloadEngine.dateUndatedFiles` renames it using the RSS feed's publish time, or else the `upload_date` recorded in `videos.jsonl` (playlists have no feed dates); without that the library would ignore the file.
- **Deleting videos:** `deleteOutsideWindow` and "delete old videos" drop short files older than the creator's `days` window but always keep bookmarked ids. "Delete watched" removes watched files except bookmarks. `trash(_:)` moves one file to the Trash. In every case `archive.txt` still lists the video, so it isn't downloaded again, and its marks are kept.
- **Vine (experimental, `settings.vineEnabled`):** Curated keeps `vineBatchSize` unwatched Vines (bookmarks aside), and each download tops that back up with the next Vines from divine.video's classics feed (`api.divine.video/api/v2/videos?classic=true&platform=vine&sort=loops`), fetched with URLSession, not yt-dlp. Each Vine goes into its author's folder `vine@<Vine user ID>/` (the usual `<timestamp>_<Vine ID>.mp4`, a `.jpg` poster, `videos.jsonl` with the loop count as `view_count`, `profile.json`, `avatar.jpg`). `vine@classics/` holds `archive.txt` (every Vine ID downloaded) and `cursor.txt` (where the next download starts in the feed), and its results are in `RunState` under that key. Trim keeps the first-downloaded unwatched Vines (archive order), takes the rest out of `archive.txt` and their authors' `videos.jsonl`, and clears `cursor.txt`, so the next download walks the feed from the top and fetches them again first. Authors are made-up `Creator`s with `platform == .vine` in `AppModel.vineLibraries`, never in `config.creators`, so older builds never meet `.vine`. Vines play in Automix and a Funny category's Automix (`automixLibraries`, all of them as one creator) but stay out of `libraries`, Top lists and the age-based cleanup. Phones get them through the sync API's `vine=1` (below).
- **Playback rules (`settings.playbackRules`, `PlaybackRules`):** per form, the cards Automix leaves out (`automixOff`) and the cards that stay at 1× (`normalSpeed`), by the keys of a mix's `picked` (a category's id, `otherCard`, `vineCard`, and for 1× only `playlistCard`), plus `resumeRewindSeconds`. Only the main Automix and its picker's starting cards use `automixOff`: a category's own Automix, Top lists and Latest don't. `Playback.applySpeed` sets 1× while the current video's card is in `normalSpeed` (`speedLocked`) and leaves the chosen `speed` alone, so it returns on the next video. A long video in a playlist's queue goes by the playlist. These and the time limit are swapped with phones, newest `at` wins. Autoplay isn't: it stays each device's own.
- **Phones mirror the Mac.** A phone deletes any local video that is missing from the manifest it asked for on the next sync. Short videos come from `watchLibraries(.short)` (creators with Shorts on), long ones from `longLibraries` (creators with long videos on, then playlists). Anything that removes a video from there removes it from phones too, and so does a phone switching its Sync setting away from a form.

## Sync API (port 8765, `CURATED_SYNC_PORT` overrides)

Documented in the header of `PhoneSync.swift`: `GET /info`, `POST /pair`, `GET /manifest`, `GET /video/<id>` (Range support), `GET /avatar/<creator id>`, `GET /poster/<id>`, `POST /played`, `POST /positions`, `POST /download`, `GET /download/progress`. Everything except `/info` and `/pair` needs a bearer token. `/info` also gives `addresses` (a comma-separated string, because older iOS builds decode it as `[String: String]`), wired first: full syncs on phones find the Mac by Bonjour and use the first of these they can reach, so its IP can change freely and a wired Mac gets used over its Wi-Fi address. `syncAPIVersion` is 10. API 10: `GET /creators/form` describes the add-creator form (fields with a type, choices, range, default and `showIf`; every value a string), and `POST /creators` answers `{added, message, creatorID?, fieldErrors?, formChanged?}`, with the values checked against that same description. Phones draw only what the form says, so a new option goes in `creatorForm` and the phones show it without changing. Change `CreatorForm.currentVersion` only when a field's meaning changes. The manifest's `longForm` marks channels with long videos on, with or without any yet. `GET /creators/<id>/older` is server-sent events of a creator's long videos not downloaded yet (leaving stops yt-dlp), `POST /creators/<id>/older` downloads the picks as the picker does, and `GET /older-thumbnail/<id>` proxies a thumbnail. `SyncResponse.deferred` is for answers that take a while. API 9: long videos picked by hand have `pickedAt`, and phones put them first until watched. API 8: `/positions` also swaps `playback` (`PlaybackRules` with `timeLimitMinutes`; the newest `at` wins, and the reply is always the Mac's result), so playback settings changed on any device reach the others. API 7: `GET /download/progress` follows a download as server-sent events (`SyncResponse.events`), one a second, each `data: {downloading, progress?, done?, total?, current?, lastDownloadAt?}`. The Mac closes the connection after the first event with `downloading: false`, so asking with nothing running gets one event, and a failed send ends it when a phone goes. It only sees downloads in the app: the overnight job is another process. API 6: `POST /download` is a phone's Force Download: it starts what Download All Now does (`AppModel.downloadAll`) and answers `{"started", "message"}`. It doesn't start while a download runs, the overnight job holds the lock, or the long-video picker is open (starting would lose its picks). The manifest's `lastDownloadAt` is `RunState.lastRun`, read from `state.json` because the overnight job writes it from another process: any run that finished and wasn't stopped, even if some creators failed. API 5: `/positions` also swaps `nowPlaying` (`{id?, at}`, newest wins; no `id` means closed or finished): the long video last playing on any device, in `nowplaying.json`. A device showing long videos with nothing playing loads it paused where it was left (`Playback.loadSyncedVideo`); phones send positions every minute while locked and playing. API 4: `POST /positions` (phones call it on opening, on leaving a video and in full syncs; a Mac without it answers 404, which phones ignore). API 2: `/manifest?forms=short,long` (or `long`) adds long videos, with `"form": "long"`, `title`, `details` and `hasPoster`, and playlists as creators with `playlist` and `order`. API 3: `&vine=1` adds the Vines (while Vine is on and `forms` includes short) as short videos under creators with `"vine": true`, plus `vineCategories` (the category ids whose Automix plays them); `/video` and `/avatar` serve them too. Phones that don't ask never see them. A plain `/manifest` is short videos only, exactly what phones from before long videos expect. Each video is sent once: one that's in a playlist and also a creator's long video comes under the creator, and the phone builds the playlist from `order`. Phones already installed may be older builds, so add fields as optional and never change existing ones. The Android `Model.kt`/`SyncClient.kt` and iOS `Model.swift`/`SyncClient.swift` decode the same payloads.

## Testing

- Use a debug build with its own data dir and port: `swift build && CURATED_DATA_DIR=<scratch dir> CURATED_SYNC_PORT=18765 CURATED_TEST_PAIRING_CODE=123456 .build/debug/Curated`. The scratch `config.json` needs `"syncEnabled": true` and a scratch `libraryPath`. Never point either at the real folders.
- The test app auto-plays Automix, so use silent test videos.
- Debug builds take `CURATED_TEST_SELECT=latest|automix|manage|creator:<id>` to open a screen without clicking, `CURATED_TEST_UPNEXT=1` to open the Up Next panel, and `CURATED_TEST_MANAGE=1` to open a creator gallery in Manage Videos mode. `CURATED_TEST_FORM=long` starts in the long sidebar. `CURATED_TEST_PICK_LONG=1` (with `CURATED_TEST_SELECT=manage`) opens the long-video picker, `CURATED_TEST_PICK_SUGGESTED=1` the suggestions picker; `CURATED_TEST_PICK_OLDER=<creator id>` a creator's older-videos picker (`CURATED_TEST_LOAD_MORE=1` presses Load More once); `CURATED_TEST_SUGGESTIONS=<file>` replaces the home feed with yt-dlp JSON lines, and `CURATED_TEST_START_PICK=<height>` downloads every suggestion at that resolution. `CURATED_TEST_THEN_MANAGE=1` opens Creators & Downloads 3 s in, after the selected screen starts playing (for the sidebar's Now Playing bar). `CURATED_TEST_SETTINGS=<pane>` opens Settings on that section (downloads, playback, storage, phone, ipod, appearance, advanced; `CURATED_TEST_IPOD_EXPORT=mix|long` starts a mix, or every long video, as Settings > iPod opens; `CURATED_TEST_SCROLL=bottom` scrolls Downloads or Storage to its end), and `CURATED_TEST_CONTROLS=1` keeps the player's controls up, for snapshots. `CURATED_TEST_SPEED=<rate>` starts at that speed, starts a held launch mix after 3 s, and prints what each video really plays at. `CURATED_TEST_SNAPSHOT` can't draw sidebars or glass; use `screencapture -l <window id>` on the test copy instead. The bare debug binary uses the `Curated` defaults domain, not the real app's `local.curated.app`.
- With a non-default port, USB sync only touches emulators (or `ANDROID_SERIAL`), never a real phone.

## Conventions

- Every commit appends an entry to `CHANGELOG.md` (oldest first): `## YYYY-MM-DD · Short title` with user-facing bullets, or `## X.Y · YYYY-MM-DD` for a release.
- Keep feature parity in mind: a user-visible change here usually needs matching work in the Android and iOS apps.
